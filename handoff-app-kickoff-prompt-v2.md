## Multi-user vs. multi-tenant — these are different, and only one is in scope now

- **Multi-tenant** = isolating separate *customer companies'* data from each other. This is the "sell to other subcontractors" concern. Deferred — not needed for an internal Einbau tool.
- **Multi-user** = multiple people *within Einbau* (estimators, the assignment team, PMs, admin) each with their own login, role, and an audit trail of who did what. **This is required now**, not deferred — every gate-resolution and PM-assignment-override action needs a real "who" attached to it.
- **Decided: use Einbau ID** (the shared session-token login already used by PUNCH/SCOUT/INTAKE, backed by `auth-worker`) rather than Entra ID SSO — stay consistent with the rest of the suite rather than standing up a second, parallel auth system. Extend it with a `role` field for this app's needs; it already ties actions to a real logged-in user, which is the actual requirement here.
- Roles needed at minimum: Estimator, Assignment Team, PM, Admin.

## The problem this app solves

Today, when an estimate is won and pushed into Procore's Portfolio as a live project, several things are supposed to happen and don't happen reliably:

1. The estimator is supposed to fill out the project's admin page properly (PO number, tender emails attached) — this is done inconsistently, and PMs/Ops end up redoing work the estimator already had the answers to.
2. The project's address doesn't reliably carry over from the estimate into the new project record (a known Procore quirk, not something to "fix" upstream — work around it).
3. The customer isn't reliably matched against the existing Procore Directory or set on the project.
4. Project assignment today is a manual email: estimating emails the assignment team, who manually reason about who's available, reply, and then a third person has to go update the project's PM field by hand.
5. There is no real handoff to the incoming PM — no documents, no email trail, no scope summary, no meeting. They inherit a project cold, and Ben personally ends up cleaning up the resulting mess.

HANDOFF automates all of this without waiting on Procore to fix any of it natively.

## Core workflow

1. **Trigger — webhook plus a reconciliation safety net, not webhook alone.** Procore's Webhooks API is real and supports company/project-scoped subscriptions to Create/Update/Delete events on various resources, including "Bids." However, Procore's own docs explicitly warn integrators to expect retries and duplicate deliveries, and there's a documented history of delivery delays plus unresolved community reports specifically around webhook reliability for Change-Order-adjacent resources. **Do not rely on the webhook alone.** Build it as the fast path for near-instant lockout, and add a periodic reconciliation poll (checking for any newly-created project not yet processed) as a safety net — cheap to add given polling infrastructure already exists elsewhere in this stack, and it guarantees nothing is permanently missed if a delivery silently fails.
2. **Lock**: on detecting the new project (via webhook or the reconciliation poll), immediately PATCH it into a holding Project Stage (e.g. "Pending Setup") via the Procore API. The project should not be usable or visible as active, and PM-assignment should not fire, until the gate below is cleared.
3. **Purgatory gate — as forceful as is actually achievable.** There is no mechanism for any third-party integration to hijack a user's browser/session and force navigation — that's not unique to this build, it's not possible for anyone. What *is* achievable and should be built: the project itself is inert (locked stage, invisible as active, no PM assignment) until the gate clears, so ignoring the notification is a dead end, not a shortcut. Pair this with an escalating notification cadence — Teams message, then email, then visibility to the estimator's manager after a timeout — so ignoring it has a real, growing cost.
4. **On submit**: the project is unlocked (stage moves out of "Pending Setup"), and PM assignment kicks off automatically.
5. **PM assignment**: workload/affinity data plus a scope summary and comparison visuals are presented; a recommended PM is proposed; the assignment team can accept or override.
6. **Handoff brief**: once a PM is confirmed, a Claude-generated summary (scope, challenges, client requirements, billing notes) is emailed to the PM and persisted in this app's own queue/dashboard. See "Handoff brief generation" below for what feeds it.
7. **Gaps**: anything left blank or explicitly deferred during the gate step generates a follow-up prompt — first to the estimator if it's their gap, later to the PM if it surfaces at handoff. Reuse one generic gap-resolution UI component for both roles.
8. **Startup tasks**: on successful handoff, a small extensible list of automated startup actions runs — first one is creating a Resource Planning request in Procore for the project's confirmed timeline. Build this as a list of discrete steps, not a single hardcoded action, since more will be added later.

## Purgatory page — required tasks (estimator-facing)

Each of these needs either a completed value or an explicit "why not yet" reason that gets carried forward as a flag (never silently dropped):

- **PO document**: drag-and-drop upload, attaches to the Procore project via API. If not available yet, capture a reason.
- **Tender emails — self-report plus automated verification, not self-report alone.** Flow: estimator checks "I've attached the tender correspondence" → short delay (uploads may take a moment to register in Procore) → automated GET against Procore's attachments/correspondence data for that project confirming it actually exists → if missing, check once more after another delay → if still missing, send the estimator back to the same screen with "this isn't showing up yet — try again or tell us why." The design goal is that falsely claiming completion costs the same effort as actually doing it. Consider generalizing this self-report-plus-verify pattern to any gate task with a checkable backing artifact, not just tender emails.
- **Project address**: resolve automatically first — check whether the source bid/estimate record has a structured address field that just isn't carrying over (likely fix: read it directly from the source record and write it to the new project, bypassing whatever Procore step is dropping it). Only fall back to document parsing if no structured source exists. Always show the resolved address to the estimator for a one-click confirm before finalizing — downstream PM-assignment logic depends on it being right.
- **Customer**: resolve the customer name from the estimate, fuzzy-match against the existing Procore Directory.
  - High-confidence match → auto-fill, referencing the existing Directory company.
  - Low-confidence/no match → stop and ask the estimator to confirm or search manually.
  - **On create (new customer): do not attempt to bypass the Directory requirement.** Procore's own documentation confirms that adding a company at the *Project* Directory level automatically propagates it to the *Company* Directory — it's one action, not two. The "Customer" field also appears to be backed by a real Directory reference (Procore's custom-fields system has an explicit "Company" field type that references the Project Directory), suggesting it's a genuine foreign key, not free text. So: create the Directory entry via API as part of setting the customer — one coordinated write — rather than searching for an API bypass that likely doesn't exist and would risk breaking whatever else expects Customer to be a valid Directory reference. **Confirm this exact cascade behavior with one sandbox test before building around it.**
- **Extensible checklist**: there will be more items than this list eventually. Build the checklist itself as data (a configurable, project-type-aware list), not hardcoded UI — reuse the same underlying concept as PUNCH's existing project-type-aware checklist feature rather than building a second, parallel checklist engine. Correction: PUNCH's registry isn't T&M-vs-Contract — it spans five types (T&M, Contract, Service Call, Warranty, Overhead). HANDOFF likely only ever needs a subset of those, since it only fires when an estimate becomes a project — Overhead and Warranty projects probably don't come through that pipeline at all. **Confirm with Ben exactly which project types actually get created via the estimate→project flow** before assuming the full five-type list applies here.

## PM assignment engine

- Only consider projects in "Active" stages — Ben will provide the exact list of stage names to filter on; don't hardcode a guess.
- Aggregate, per PM, across their active projects: project count, total contract value, and **timeline overlap** (not just count — a PM with three projects all wrapping up this month has more real capacity than one with three projects all just starting).
- **Do not build headcount-on-site scoring in this first version.** When it's added later, it should come from time-windowed Resource Planning ("RP") assignment data matched to the *new* project's date range, not just a current snapshot.
- **Do not build geographic distance scoring.** Instead, build an admin-editable table of PM ↔ region/client/job-type affinity (a preferred PM and a weight per combination) — this captures real institutional relationships and preferences that pure distance math would miss.
- **Present a scope summary alongside comparison visuals** (workload, contract value, timeline overlap across candidate PMs) to support the human decision — not text-only. Recharts is a natural fit given the existing React/Vite stack.
- Claude synthesizes a short recommendation plus reasoning from the aggregated numbers and the affinity table. The assignment team can accept or override — always override-able, never a silent auto-assign.
- On confirmation, PATCH the project's assigned-PM field directly — this removes the current "someone else updates it manually" step.

## Handoff brief generation

- **Inputs**: the PO document, tender correspondence, and any other documents gathered by this point, plus estimate data — total cost, labor hours, margin. **Confirmed source (Ben, live screenshot): this data lives natively in Procore's own project-level Estimating tool** (Overview/Documents/Takeoff/**Estimating**/Proposal tabs on the project) — a "Summary" view with cost-item-type rows (Labor, Materials), total labor hours, difficulty factor, waste %, total cost, margin %, total sales, and an Estimate Total, all computed by Procore itself. Pull from here, not from NetSuite Opportunity fields — this sidesteps the SCOUT→NetSuite write-leg risk noted in the addendum entirely, since this data never has to leave Procore. Still needs verifying: the REST API surface for the Estimating tool's data. `procore-worker` already has a proven `/estimating/...` namespace (`/estimating/bid_board_projects`, v2.0) for Bid Board — check whether a sibling `/estimating/` endpoint exposes this project-level Estimating summary before assuming it needs a fresh integration.
- **New required step — rename the source estimate record(s) once a PO number is captured.** Since SCOUT already keeps the NetSuite Opportunity and the Procore Bid Board entry linked (its existing "Link Records" pattern PATCHes the Procore Bid ID back to NetSuite once both exist), this rename should follow the same linked-record approach and update both records, not just one — otherwise this reintroduces the exact kind of drift SCOUT's linking was built to prevent.
- **Output**: a structured brief — scope of work, known challenges/open items, client-specific requirements, billing/invoicing quirks, key contacts and dates.
- **Delivery**: emailed to the assigned PM, and persisted in this app's own queue/dashboard as a re-visitable record.
- Any information gaps identified while generating the brief reuse the same gap-resolution UI component used on the estimator side.
- **Explore (not committed): automatic extraction of marked-up drawings for inclusion in the brief.** This is genuinely harder than receipt/document parsing — drawing sets can run to hundreds of pages, so "find the marked-up ones" needs a cheap triage pass to identify pages with visible markup before running anything more expensive on them, or cost scales badly with drawing-set size. Treat as a prototype to evaluate, not a day-one commitment.
- **Start building the "Back of House SOW" now, even though the copilot chat itself is deferred.** As HANDOFF processes each project's documents, tag and retain a curated set — crucial documents only, parsed takeoffs and interpretations, not every email and attachment ever generated. This becomes the retrieval corpus for the future project-scoped copilot (see below) — assembling it progressively now means there's a real corpus to embed later instead of reconstructing one retroactively.

Gathered from actually building and breaking things across this stack over the last several days, not from re-reading these docs. Company ID `562949953508586` is confirmed correct — it matches what's already live in `procore-worker`.

**Open Question #1 (confirm INTAKE naming) — answered, but correcting a mixup, not confirming the original guess.** The original doc guessed INTAKE was the expense/receipt-parsing tool (email → Claude parsing → review queue → Direct Cost) — that's wrong, that's **TALLY**, a separate app currently being built out, not critical to HANDOFF. INTAKE is something else: live in production, both a standalone app and a popout embedded in SCOUT, and it already does almost precisely what HANDOFF's "Customer" gate task needs — fuzzy-match a company name against the existing Procore Directory, split into a high-confidence auto-fill path vs. a low-confidence "confirm or search manually" path, and create-on-Directory when there's no match. This isn't theoretical: it shipped, and it's already survived two real bugs worth knowing about before HANDOFF reimplements the same logic blind — (1) a race condition where two overlapping duplicate-check calls could both render instead of the second replacing the first (fixed with a generation-counter guard), and (2) an entity-type check that broke after a "pick an existing company" flow made one field always read the same value regardless of whether the match was a customer or a vendor. Look at `scout-intake/index.html`'s duplicate-match and existing-company logic before building HANDOFF's customer-matching from scratch.

**An open risk — narrower now than originally flagged, but still real for anything else that leans on NetSuite Opportunity.** This addendum originally warned that cost/hours/margin "likely lives in NetSuite Opportunity fields SCOUT writes to," and that SCOUT's NetSuite-write leg (a Power Automate flow hitting `netsuite-worker`) was silently broken this week by an auth-gate fix that didn't add a service-key bypass for Power Automate at the same time (PA doesn't fail a run visibly on a non-2xx by default, so it had zero visible symptoms, and **was never confirmed fixed** before that thread moved on). Ben has since confirmed the cost/hours/margin data actually comes straight from Procore's own Estimating tool (see "Handoff brief generation" above), not NetSuite — so that specific pull sidesteps this risk entirely. Still worth knowing the underlying fact if HANDOFF ends up needing *anything else* that flows through that same SCOUT→NetSuite write leg: verify `netsuite-worker` has a working service-key path for PA before depending on it. SCOUT's *customer lookups* are confirmed fine separately — those go directly to `netsuite.ben-a90.workers.dev`, not through any PA flow.

**The shared auth pattern — decided: HANDOFF stays on it, no Entra ID.** Every sibling Worker (`punch-worker`, `netsuite-worker`, `scout-worker`, `procore-worker`) was hardened this session against a real vulnerability — all were fully open, their URLs visible in public frontend source, callable by anyone with no login at all. The pattern now standard across all four, and what HANDOFF should use too (per Ben, see Multi-user section above): browser callers authenticate via **Einbau ID** (a shared custom session-token system, `auth-worker`, `/auth/verify`), and non-browser callers (Power Automate, anything server-to-server) use a static `X-<Name>-Service-Key` header checked *alongside* — never instead of — the session check. Einbau ID already ties actions to a real logged-in user; it just needs a `role` column added for Estimator/Assignment/PM/Admin. One Worker-to-Worker gotcha regardless of auth choice: a plain `fetch()` from one Worker to another's `*.workers.dev` URL gets blocked with Cloudflare error 1042 — use a Cloudflare **service binding** (`env.AUTH_WORKER.fetch(...)`) instead, which is how every existing cross-Worker call in this stack works.

**Correction, not a decision — PUNCH does NOT go through `procore-worker`, and neither does TALLY.** This paragraph originally claimed "SCOUT, INTAKE, and PUNCH all call Procore through [`procore-worker`] today" — that's wrong for PUNCH, verified directly against `punch-worker/src/index.js`: it has its own `getProcoreToken()` and its own `PROCORE_CLIENT_ID`/`PROCORE_CLIENT_SECRET`/`PROCORE_COMPANY_ID`, calling `api.procore.com` directly. Checked `TALLY/worker/src/index.js` too — identical shape, its own independent Procore credentials. So the real picture: `procore-worker` is a shared proxy used only by SCOUT and INTAKE, both of which call it **from the browser**, using the logged-in user's own Einbau ID session to authorize each call. PUNCH and TALLY don't do that at all — their backend Workers run server-side with no user session driving each Procore call, so each just holds its own Procore app credentials directly, the same way `procore-worker` itself does.

HANDOFF's Procore calls (webhook processing, reconciliation poll, PM-assignment aggregation) are all server-initiated with no browser session in the loop — the same shape as PUNCH/TALLY, not SCOUT/INTAKE. So there are two legitimate options, not one obvious answer: (a) give HANDOFF its own Procore `client_credentials` app, matching the pattern of the sibling that's actually closest in shape (PUNCH/TALLY) — more credentials to manage suite-wide, but no dependency on another Worker's uptime; or (b) service-bind into `procore-worker` anyway (`env.PROCORE_WORKER.fetch(...)`, matching the `AUTH_WORKER` service-binding pattern, plus the `X-Procore-Service-Key` header since there's no browser session to authorize with) — fewer places holding the Procore secret, at the cost of coupling HANDOFF's Procore access to `procore-worker` staying up. Worth deciding deliberately rather than assuming either way.

**A `wrangler deploy` footgun that already caused a real incident this week:** deploying from a `wrangler.toml` with no `[vars]` section is treated as authoritative by Cloudflare and silently **wipes** any plain (non-secret) environment variables previously set on that Worker in the dashboard — encrypted secrets survive since wrangler doesn't touch vars it doesn't reference, but plain vars don't. This actually happened to `procore-worker` (wiped `PROCORE_CLIENT_ID`/`PROCORE_COMPANY_ID`) and cost a multi-day credential-recovery scramble. If HANDOFF's Worker holds any plain vars, make sure `wrangler.toml` declares `[vars]` explicitly before the first deploy, not after.

**Cloudflare's real per-invocation subrequest ceiling is lower than documented** — confirmed empirically on this account/plan: 25 parallel subrequests failed, 8 succeeded. This is directly relevant to the PM-assignment engine's per-PM aggregation (workload, contract value, timeline overlap across every candidate PM's active projects) and the reconciliation poll — batch API calls in groups of ~8 from day one rather than discovering the ceiling after a production failure, and prefer bulk endpoints/bulk inserts over per-item loops where Procore/Postgres support them.

**A real, confirmed Procore API bug relevant to the reconciliation poll and any other date-filtered query:** the `filters[created_at]` query parameter is silently ignored on at least Timesheets/Direct Costs/Requisitions endpoints — confirmed live, a supposed 1-hour window returned results over a year old. Don't trust server-side date filtering on Procore endpoints for "find anything new since X" logic; fetch and filter client-side against the real `created_at` field, or confirm date filtering actually works on whichever specific endpoint the webhook/poll targets before relying on it.

**Procore's Company Directory shape, relevant to Open Question #6 and the "Customer" gate task:** the `/vendors` endpoint holds *every* company in the Directory regardless of real-world relationship — customers, subcontractors, even Einbau's own company record appears there (`company_vendor: true`). There's no separate "customers" endpoint. Also, INTAKE's build already empirically observed the exact cascade this doc's Question #6 asks about — adding a company at the Project Directory level does propagate automatically to the Company Directory — for whatever that's worth as a second data point ahead of HANDOFF's own planned sandbox test.

**PUNCH checklist correction — applied above in the "Extensible checklist" bullet.** It's a unified registry (`CHECKLIST_REGISTRY` in `PUNCH/punch-bubbles.jsx`) spanning five project types (T&M, Contract, Service Call, Warranty, Overhead), not a T&M-vs-Contract binary, with `buildChecklist()` filtering per type and preserving each item's `key`/`done` state across type changes. More relevant to HANDOFF than the data shape, though: PUNCH already has a working precedent for exactly the "self-report plus automated verification" pattern this doc specs for the tender-emails gate task — a subset of checklist items (`CHECKLIST_DETAIL_ITEMS`, same file) are backed by a live read into Procore rather than a plain checkbox, so the UI reflects real Procore state instead of trusting a click. Worth reading that mechanism before building HANDOFF's gate-verification flow from scratch, since it's already been tuned against real Procore API behavior.
